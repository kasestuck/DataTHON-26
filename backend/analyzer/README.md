## Запуск из корня репозитория, PowerShell

```powershell
# Окружение проекта уже создано. На чистой машине:
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-analyzer.txt

.\.venv\Scripts\python.exe -m backend.scripts.check_environment
.\.venv\Scripts\python.exe -m pytest -q

# Только после согласования загрузки ~4.35 GB и успешной проверки CUDA:
.\.venv\Scripts\python.exe -m backend.scripts.download_models
.\.venv\Scripts\python.exe -m backend.scripts.smoke_models
.\.venv\Scripts\python.exe -m backend.scripts.smoke_models --oom-check --output backend/data/reports/oom_smoke.json

# Исходный импорт уже выполнен. Повторный исходный импорт требует новый --output,
# чтобы случайно не стереть ручную классификацию.
.\.venv\Scripts\python.exe -m backend.scripts.import_labels --excel dataset/open_labels.xlsx --videos-dir dataset/videos

# После заполнения ручной таблицы (CSV UTF-8 или XLSX):
.\.venv\Scripts\python.exe -m backend.scripts.import_labels --manual backend/data/manual_labels.xlsx

# Сгруппировать описания по обсуждаемым визуальным критериям:
.\.venv\Scripts\python.exe -m backend.scripts.prepare_annotations --catalog backend/data/annotations/catalog_pending_review.json
# Сохранить предложения для ручной проверки; неподтверждённые ID не активируются:
.\.venv\Scripts\python.exe -m backend.scripts.apply_annotations
# После явной ручной проверки соответствий:
.\.venv\Scripts\python.exe -m backend.scripts.apply_annotations --confirmations backend/data/annotations/human_confirmations.json

# Применение последнего задания пользователя (актуальный рабочий импорт):
.\.venv\Scripts\python.exe -m backend.scripts.finalize_labels

.\.venv\Scripts\python.exe -m backend.scripts.benchmark
.\.venv\Scripts\python.exe -m backend.scripts.evaluate
# Продолжить прерванный проход только с теми же данными, моделями и кодом:
.\.venv\Scripts\python.exe -m backend.scripts.evaluate --resume
# Приватные таблицы всех результатов/ошибок и реальные JPEG-доказательства:
.\.venv\Scripts\python.exe -m backend.scripts.report_results
.\.venv\Scripts\python.exe -m backend.scripts.export_evidence
# После отдельного согласованного размещения весов:
.\.venv\Scripts\python.exe -m backend.scripts.benchmark --full
```

Текущее окружение использует `--system-site-packages` для уже установленных NumPy,
openpyxl и pytest. Установка OpenCV выполнена внутри `.venv`. Для изолированного
развёртывания создайте обычную venv и установите файл зависимостей.

Excel: фактические колонки `наименование файла`, `таймстемп`,
`нарушение / без нарушения`; в обновлённом файле описания находятся в столбце D
(`--description-column` для другого расположения). Поддерживаются русские значения, числовые секунды,
`MM:SS`, `HH:MM:SS`, `1минута 8 секунда`, Excel time/timedelta. Число в обычной
числовой ячейке трактуется как секунды; доли суток автоматически не угадываются.
Дополнительные имена можно задать `--columns '{"video":"имя", ...}'`, лист — `--sheet`.
Латинская `X` и кириллическая `Х` сопоставляются, но коллизии реальных имён — ошибка.
Дубли исходных видео и отсутствующие файлы по умолчанию останавливают импорт.
`--allow-missing` сохраняет строки и явно перечисляет отсутствующие файлы в отчёте.

## Ручная классификация

Актуальная разметка этого этапа применяется через `backend.scripts.finalize_labels`
из Excel и отдельного документа решений пользователя. Старые
`grouping_proposals.json`/`catalog_pending_review.json` сохранены как история
проверки и не являются источником текущих меток. Скрипты группировки и
`apply_annotations` нужны для новых предложений; повторный запуск старых
предложений не заменяет актуальные уточнения пользователя.

Используйте `backend/data/manual_labels_template.csv` с колонками:
`video,timecode_sec,observed_action,violation_type,notes`.
Пустой шаблон не содержит вымышленных примеров. Каждое событие требует времени,
наблюдаемого действия и подтверждённого пользователем типа. Можно указать несколько
событий одного видео; одинаковые события запрещены. Таблица заменяет события
перечисленных в ней видео целиком, остальные видео сохраняются. Для отрицательных
видео разрешены строки с пустыми `timecode_sec` и `violation_type`: наблюдение и
заметки сохраняются, новый тип не создаётся. Противоречие с
исходным отрицательным вердиктом требует явной проверки исходной разметки.

Каталог соответствует контракту Back 2:
`{"type_id":{"name":"Название для пользователя","description":"Визуальные признаки"}}`.
Дополнительных полей и нормативных оснований в нём нет. Ручной импорт принимает
только ID, уже имеющие визуальные критерии в каталоге, и записывает `confirmed`.
Неоднозначную положительную строку можно импортировать с дополнительным столбцом
`review_status=needs_review`: она останется `unknown`. Исходный текст находится
в `observed_action`, происхождение — в `source_row` и `source_sha256`.
`unknown` и `needs_review` не являются классами. Обучения в коде нет.

`prepare_annotations` использует только установленную локальную Qwen3-VL для
предложений группировки; это не ручное подтверждение ID. `apply_annotations`
проверяет SHA-256 источника, полное однократное покрытие строк, отрицательные
вердикты и признаки неопределённости. Только категории с явным ручным
подтверждением становятся активными. Документ подтверждений содержит
`source_sha256` и `events: [{source_row, type_id}]`; локальная модель его не создаёт.
Копия предыдущего CSV сохраняется перед
заменой. Подробный список на проверку — `backend/data/needs_review.csv`.
Все исходные описания, ответы локальной модели и отчёты исключены из Git.

## Контракт для Back 2

```python
from backend.analyzer import analyze_video, Finding, ModelNotConfiguredError

def main():
    findings: list[Finding] = analyze_video("dataset/videos/X-1.mov")
    # Finding: violation_type, timecode_sec, description, confidence, evidence_frames
    # EvidenceFrame: timestamp_sec, jpeg_bytes (bytes; API кодирует их самостоятельно)

if __name__ == "__main__":  # обязательно для Windows multiprocessing в скрипте
    main()
```

В сервере вызывайте функцию из обработчика/сервисного слоя, не при импорте модуля.
Вызов синхронный. Для отладки доступны `Analyzer`, `AnalyzerConfig` и
`analyze_video_report` в соответствующих модулях; HTTP endpoint здесь отсутствует.

Стандартные директории `models/rtdetr_r18vd` и `models/qwen3_vl_2b` подхватываются
автоматически. Для других путей:

```powershell
$env:ANALYZER_DETECTOR_DIR = (Resolve-Path models/rtdetr_r18vd).Path
$env:ANALYZER_VLM_DIR = (Resolve-Path models/qwen3_vl_2b).Path
$env:ANALYZER_CONFIDENCE = "0.75"
# необязательно: ANALYZER_CATALOG — путь к проверенному каталогу
```

При отсутствии моделей — `ModelNotConfiguredError`, при ошибке декодирования —
`VideoReadError`, при ошибке inference/JSON/OOM — `InferenceError`, при превышении
времени — `AnalysisTimeoutError`. Ошибки не превращаются в отрицательный вердикт.
Успешный анализ без подтверждённых находок возвращает `[]`. При пустом каталоге
допустимы только диагностические наблюдения; они доступны в отчёте и не являются
нарушениями. Любой положительный ответ вне каталога или окна доказательств — ошибка.

По умолчанию: 2 FPS, максимум 640 px по длинной стороне, потоковая обработка,
6 кадров из контекста до 10 секунд, до 12 окон на видео, 1–3 JPEG-доказательства на находку,
порог 0.75, устранение дублей одинакового типа в пределах 4 секунд.
Оценка уверенности самой VLM не калибрована; порог требует проверки на разметке.
Нормализованные bounding boxes не определяют роли. IoU-трекинг связывает объекты
только между соседними выборками; это не идентификация человека. COCO-детектор
не умеет надёжно распознавать банкноты или нарушения кассовой дисциплины.

Окна содержат контекст до/после события и периодические выборки. Минимальный
интервал между окнами зависит от длительности видео, чтобы бюджет не расходовался
полностью в начале. Такой отбор может пропустить короткое/малозаметное действие.

Декодирование однопроходное. В памяти держится ограниченное окно, а не всё видео.
Времена кадров всегда `frame_index / FPS`; для VFR это приближение по среднему FPS,
а не точные PTS контейнера. Произвольный seek в MOV может выдавать неверный кадр,
поэтому `at()` также считает декодированные кадры от начала. Ранний обрыв — ошибка.

Публичный вызов запускает один процесс с обеими моделями и завершает его при
превышении 260 секунд, включая загрузку весов. Это оставляет запас до 270 секунд Back 2.
На VLM выделено до 35 секунд на окно, включая один ограниченный повтор при
неверной JSON-схеме; после него ошибка не подменяется отрицательным ответом.
Модели загружаются заново на каждый вызов: это простой способ ограничить зависание
декодера/CUDA и освободить VRAM после OOM. Инициализация включена в `wall_sec`.
Back 2 должен ограничить одновременную обработку на этой GPU одним видео.
Прямой `Analyzer.analyze()` проверяет дедлайн между операциями; жёсткое ограничение
обеспечивает именно `analyze_video_report`/`analyze_video`.

Никакие обученные веса не скачиваются без предварительного подтверждения размера.
Явная команда `download_models` относится только к подготовке окружения: она
проверяет лицензию метаданных, фиксирует revision и сохраняет provenance внутри
игнорируемого `models/`. Она не принимает частные видео и не вызывается анализатором.
Двухбайтовые веса альтернативы занимают приблизительно 4.26 GB (около 3.96 GiB) без runtime.
На длинном ролике измерен пик PyTorch allocator 5.03 GiB. Дополнительно память
занимают контекст драйвера и другие приложения; пик зависит от входных данных.
Совместный smoke-test на синтетическом видео прошёл с пиком 4.63 GiB.
Нативная AWQ-сборка для этой Windows/Python
не проверена; используется SDPA из самого PyTorch, без внешних FlashAttention/Triton.

Официальный [индекс CUDA 12.8](https://download.pytorch.org/whl/cu128/torch/)
содержит PyTorch 2.10.0 для Windows/Python 3.13. Версия CUDA в `nvidia-smi` —
возможность драйвера, а не доказательство установленного Toolkit или CUDA PyTorch.
Для PyTorch wheel отдельный Toolkit не требуется; результат GPU-проверки даёт
`check_environment.py`, включая настоящий запуск матричного ядра.

CUDA-проверка пройдена: `torch==2.10.0+cu128`, доступность CUDA и матричное ядро
подтверждены на RTX 4060 Laptop (драйвер 610.62). Опциональные Python-библиотеки:

```powershell
.\.venv\Scripts\python.exe -m pip install torch==2.10.0 torchvision==0.25.0 --index-url https://download.pytorch.org/whl/cu128
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-models.txt
```

Их установка не загружает обученные модели.
Нейросетевые адаптеры используют только локальные директории, safetensors,
`local_files_only=True` и `trust_remote_code=False`. Рабочий процесс устанавливает
offline/telemetry flags до импорта библиотек. Аудит процесса запрещает DNS и
сетевые соединения. Сетевых клиентов в pipeline нет.
Функция не сохраняет видео/кадры. Аудио не извлекается, лица не распознаются.
Некорректные ответы модели сохраняются приватно для диагностики внутри временного корня.
Кеши библиотек и CUDA направлены в `backend/analyzer/output/runtime-cache`;
другой разрешённый временный корень задаётся `ANALYZER_TEMP_DIR`.

`evaluation.json` и `evaluation_release42.json` содержат результаты одной
фиксированной конфигурации: 42 реальных MOV, 22 исходных положительных и

Веса, конфигурация, код, каталог, политика и разметка зафиксированы в `run_inputs`;
fingerprint: `61fbb57ce56b1b820c71817cdf0b25df5745af0bfed4661364e26374e5e1e1ba`.
Проверка `evaluate --resume` успешно восстановила все 42 результата без новых
вызовов моделей. Промежуточные эксперименты не включены в итоговые метрики.

| TP / TN / FP / FN | 11 / 11 / 9 / 11 |

Это обнаружение любого визуального шаблона на уровне видео: совпадение
бинарного вердикта не подтверждает правильность конкретного типа и времени.
Юридическая доказанность исходных меток не оценивалась.

Локализация без учёта типа: ближайшее однократное сопоставление дало MAE
**6.813 с по 11 событиям**, для остальных 11 положительных видео предсказаний нет.
Из 22 исходных событий 3 совпали в пределах 3 с, 6 — в пределах 5 с.
MAE только трёх совпадений до 3 с равна 1.325 с; это ограниченная подвыборка.
При допуске 3 с событийные TP/FP/FN = 3/48/19, precision 5.88%, recall 13.64%,
F1 8.22%. Несколько ложных находок на одном видео считаются отдельно.

Для классификации доступны 3 подтверждённых визуальных события (дверь помещения
в X-32/X-33 и переход к следующей операции в X-47) плюс 20 отрицательных видео.
Правильных совпадений типа и времени до 3 с нет: micro TP/FP/FN = 0/36/3.
У единственного локализованного подтверждённого события тип ошибочен:
`cash_room_door_left_open` → `safe_door_open`; второе событие двери и переход
операций пропущены. Условная type accuracy = 0/1, сквозное покрытие подтверждённых
типов = 0/3. Эта малая выборка не оценивает достоверно все 18 категорий.
Остальные 19 положительных типов сохраняют `needs_review` и исключены из
классификационной оценки. Матрица ошибок есть в `evaluation.json`.

Отчёты этих проверок: `smoke_detector.json`, `smoke_models.json`, `oom_smoke.json`,
`benchmark_longest.json` в той же локальной папке. Содержимое кадров и наблюдений
в отчёты бенчмарка не включено. Измерение одного ролика не даёт метрик качества.

`--full` включает загрузку и выполнение настоящих моделей, без mock.
`peak_vram_bytes` — пик PyTorch allocator в рабочем процессе, не вся память драйвера.
Без моделей поля inference/VRAM/метрик остаются недоступными. Ошибки и пропущенные
видео перечислены отдельно; они не учитываются как отрицательные ответы.
Диагностические ответы с пустым каталогом также исключены из метрик.

Метрики разделены: бинарный вердикт по видео; локализация с настраиваемым допуском;
классификация по полностью классифицированным видео и отрицательным примерам.
Видео с `unknown` исключаются из классификации целиком, поскольку остальные события
в них могут быть ещё не размечены. Локализация использует однозначное сопоставление
максимального количества событий, предпочитая ближайшие рёбра. Ошибка времени
усредняется по сопоставленным событиям и сопровождается TP/FP/FN; это не ошибка
по всем пропущенным событиям. Нулевые знаменатели дают `null`.
Дополнительно считаются совпадения до 5 секунд и ошибка ближайшего однократного
сопоставления без отсечения по порогу. Последняя сопровождается числом найденных
соответствий: для видео без предсказаний ошибка времени не определена.

Устойчивость к новому ракурсу не измерена: нужны отдельные размеченные видео с
другой камеры. Синтетическое изменение геометрии не заменяет такую оценку.
Таймаут проверен синтетическим зависшим процессом, OOM — также на настоящем CUDA
allocator с принудительным лимитом. Устойчивость к физическому исчерпанию всей VRAM
внешними процессами отдельно не измерялась.
